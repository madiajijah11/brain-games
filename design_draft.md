# Centralized Auth Guard & Game Submission Integrity

*   **Author:** MexL
*   **Status:** Draft
*   **Date:** 2026-11-09

--------------------------------------------------------------------------------

## Overview

Brain Games is a responsive brain-training web application running on Next.js 16 App Router, Auth.js v5 (JWT sessions), and Neon PostgreSQL. This design document establishes two foundational stability and security improvements:
1. A centralized Edge-safe Next.js Middleware that intercepts requests to authentication guest routes (`/login`, `/register`) to redirect authenticated users to `/dashboard`, while guarding protected routes (`/dashboard`, `/games/:path*`).
2. A hardened and clock-resilient game submission pipeline on `/api/games/submit` and `components/game-runner.tsx` that eliminates distributed clock skew false-positives while enforcing strict anti-cheat duration boundaries, accompanied by private server-side diagnostic logging for rapid troubleshooting in Vercel runtime logs.

## The Problem

Users currently experience two distinct routing and gameplay defects in production and preview deployments on Vercel:

1. **Guest Route Leakage**: After logging in, navigating directly to `/login` or `/register` continues to display authentication forms instead of redirecting the user to `/dashboard`. Authentication checks are currently performed ad-hoc inside selected Server Components, leaving public entry points unguarded and creating confusing navigation loops.
2. **Game Submission Rejection (`Invalid game submission`)**: Completing a game session triggers an immediate HTTP 400 rejection with the message "Invalid game submission." This is caused by:
   - Client-server clock skew: `components/game-runner.tsx` calculates duration as `Date.now() - started`, where `started` was a timestamp generated by the server during `/api/games/start`. If the user's device clock is slightly behind the server clock, the resulting duration is negative, instantly failing the Zod schema's `min(0)` constraint.
   - Client latency or pauses exceeding the rigid 10-minute cap (`max(600000)`).
   - Opaque error handling: When validation fails, `/api/games/submit` returns a generic error string to the client and suppresses error details without emitting diagnostic logs to the Vercel serverless console, preventing operators from inspecting failure causes.

## Goals

*   **Centralized Route Interception**: Intercept all navigation to `/login` and `/register` via Next.js Middleware, redirecting users with a valid Auth.js JWT session to `/dashboard`.
*   **Edge-Safe Execution**: Ensure middleware executes in sub-10ms latency on Vercel Edge without importing Prisma or performing database queries.
*   **Clock-Independent Gameplay Timing**: Eliminate client-server clock drift errors by measuring elapsed gameplay duration via client monotonic timing (`performance.now()`).
*   **Strict Anti-Cheat Verification**: Enforce physiological gameplay boundaries on the server (rejecting automated submissions completed in < 3,000 ms for 5 questions, and sessions exceeding 600,000 ms) while strictly validating that 5 valid question IDs and answers are present.
*   **Secure Debuggability**: Maintain generic client-facing error payloads (`{ error: "Invalid game submission." }`) to protect anti-cheat validation rules, while emitting structured Zod validation diagnostics (`parsed.error.flatten()`) to Vercel Serverless runtime logs.

## Non-Goals

*   **Database-Backed Session Storage**: No database adapter or session lookups in Neon will be introduced; Auth.js remains strictly JWT-based.
*   **External Rate Limiting Infrastructure**: Dedicated Redis/Upstash rate-limiting tiers are deferred from this MVP stabilization slice.
*   **Client Code Obfuscation**: No heavy client-side anti-tamper SDKs or browser fingerprinting will be added.

## Open Questions

*   None at this time; route targets, timing protocol, and logging policies were validated during the brainstorming phase.

## Technical Plan

### 1. High-Level Architecture & Route Interception Flow

```text
Browser Request
      │
      ▼
┌────────────────────────────────────────────────────────┐
│              Next.js Edge Middleware                   │
│                    (middleware.ts)                     │
│  - Decodes Auth.js JWT from cookie                     │
│  - Zero DB / Prisma imports (Edge-safe)                │
└──────────────────────────┬─────────────────────────────┘
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
     [Target: Guest Route]      [Target: Protected Route]
     (/login, /register)        (/dashboard, /games/*)
             │                           │
     Has valid session?          Has valid session?
      ├── YES ──► Redirect               ├── NO  ──► Redirect to /login
      │           to /dashboard          │           with callbackUrl
      └── NO  ──► Pass through           └── YES ──► Pass through
```

### 2. Edge-Safe Auth Splitting Pattern

To prevent Next.js Edge runtime bundler errors, Auth.js configuration is decoupled into two tiers:
1. `auth.config.ts`: Contains Edge-compatible options (`session: { strategy: "jwt" }`, `pages: { signIn: "/login" }`, JWT/session callbacks, and empty `providers: []`). This file has zero imports of `@prisma/client` or `bcryptjs`.
2. `lib/auth.ts`: Inherits `auth.config.ts` and attaches the Credentials provider with Prisma database lookup and bcrypt verification. This file is imported exclusively in Node.js runtime environments (`app/api/**`, Server Components).
3. `middleware.ts`: Imports `NextAuth(authConfig).auth` to inspect session tokens directly at the network edge with sub-10ms overhead and zero database connections.

### 3. Gameplay Timing & Anti-Cheat Protocol

```text
Client (Browser)                                    Server (Vercel Node.js)
       │                                                       │
       ├──── POST /api/games/start { slug } ──────────────────►│
       │                                                       │ (Fetch 5 questions)
       │◄─── 200 OK { questions } ─────────────────────────────┤
       │                                                       │
[Mark local startTime = performance.now()]                     │
[User solves 5 questions sequentially]                         │
[On finish: durationMs = Math.round(now - startTime)]          │
       │                                                       │
       ├──── POST /api/games/submit { slug, answers, duration }►│
       │                                                       │ (Zod Validation)
       │                                                       │ - slug in enum
       │                                                       │ - answers.length === 5
       │                                                       │ - 3,000ms <= duration <= 600,000ms
       │                                                       │
       │                                                       │ If invalid:
       │                                                       │ ├─ Log error to Vercel console
       │◄─── 400 { error: "Invalid game submission." } ────────┤ └─ Return generic 400
       │                                                       │ If valid:
       │                                                       │ ├─ Grade answers
       │                                                       │ ├─ Atomic DB transaction
       │◄─── 200 OK { score, xpEarned, streak, results } ──────┤ └─ Return results
```

### 4. Observability & SRE Diagnostics

In `app/api/games/submit/route.ts`, whenever `submitSchema.safeParse` fails:
```typescript
if (!parsed.success) {
  console.error(
    "[GameSubmissionError]",
    JSON.stringify({
      userId: session.user.id,
      errors: parsed.error.flatten(),
      received: {
        slug: (body as any)?.slug,
        answersCount: (body as any)?.answers?.length,
        durationMs: (body as any)?.durationMs,
      },
    })
  );
  return NextResponse.json({ error: "Invalid game submission." }, { status: 400 });
}
```
This guarantees that operators can inspect exact validation rejection reasons in the Vercel Functions log dashboard without exposing security-sensitive thresholds to the client.

## Alternatives Considered

### 1. Page-Level Server Component Redirects Only

*   **Mechanism**: Execute `const session = await auth(); if (session?.user) redirect("/dashboard");` directly inside `app/login/page.tsx` and `app/register/page.tsx`.
*   **Trade-off**: Requires zero Edge middleware files and zero configuration splitting.
*   **Reason for Rejection**: *Rejected by author*. Lacks centralized enforcement, requires manually repeating authentication guards across every present and future public and private route file, and cannot uniformly preserve or manipulate `callbackUrl` search parameters across edge hops.

### 2. Fully Permissive Client-Reported Duration (Zero Server Enforcement)

*   **Mechanism**: Remove `durationMs` constraints from the server schema, accepting any integer or optional duration value.
*   **Trade-off**: Completely eliminates false positives from client timing discrepancies.
*   **Reason for Rejection**: *Rejected by author*. Violates the strict anti-cheat requirement mandated in `AGENTS.md`. Allowing zero-millisecond submissions enables automated scripts to replay submissions and harvest unlimited XP and streak milestones instantly.

### 3. Verbose Validation Error Payloads Returned to Browser

*   **Mechanism**: Return `NextResponse.json({ error: "Invalid game submission.", details: parsed.error.flatten() }, { status: 400 })` directly to the client.
*   **Trade-off**: Allows frontend developers to read exact validation errors in browser DevTools network tabs.
*   **Reason for Rejection**: *Rejected by author*. Exposing exact anti-cheat timing thresholds (e.g., minimum 3,000 ms) and validation schemas to client callers directly assists adversaries in calibrating cheating bots to evade detection.

### 4. Database-Backed Session Lookup in Middleware

*   **Mechanism**: Query Neon PostgreSQL from `middleware.ts` to verify user existence and ban status on every request.
*   **Trade-off**: Provides instant revocation of compromised accounts.
*   **Reason for Rejection**: *Rejected by author*. Next.js Edge runtime cannot execute native Prisma drivers without external proxy layers (e.g. Prisma Accelerate), and querying the database on every asset or document request risks exhausting Neon serverless connection limits and adding 50–150ms of network latency.

## Detailed Implementation Plan

### Target Files to Create/Modify

#### 1. `auth.config.ts` (Create)
*   **Type / Scope**: Next.js App / Auth.js Configuration Module (Edge-compatible).
*   **Rationale**: Defines base session strategy (`jwt`), custom authentication pages (`signIn: "/login"`), JWT/session token mappings, and an `authorized` callback for route verification. Contains zero imports of `@prisma/client`, `bcryptjs`, or native Node.js APIs, allowing it to be bundled cleanly into Vercel Edge Middleware.

#### 2. `middleware.ts` (Create)
*   **Type / Scope**: Next.js Edge Middleware.
*   **Rationale**: Instantiates NextAuth with `authConfig` and intercepts requests matching application routes. Redirects logged-in users away from `/login` and `/register` to `/dashboard`, and unauthenticated users accessing `/dashboard` or `/games/:path*` to `/login?callbackUrl=...`. Configures a strict matcher excluding `api/`, `_next/static/`, `_next/image/`, and static assets (`favicon.ico`, etc.).

#### 3. `lib/auth.ts` (Modify)
*   **Type / Scope**: Server Authentication Module (Node.js runtime).
*   **Rationale**: Refactors existing `NextAuth` instantiation to spread `authConfig` and append the database-backed Credentials provider with Prisma and bcryptjs. Retains existing exports (`handlers`, `auth`, `signIn`, `signOut`) so existing Server Components and Route Handlers continue working without breaking changes.

#### 4. `components/game-runner.tsx` (Modify)
*   **Type / Scope**: React Client Component.
*   **Rationale**: 
    1. Replaces mixed server/client timestamp subtraction (`Date.now() - startedAt`) with pure client-side monotonic timing using `performance.now()`.
    2. Initializes `startTime` when questions load into state, and computes `durationMs = Math.max(0, Math.round(performance.now() - startTime))` upon submission.
    3. Handles initial state edge cases to ensure `durationMs` is always an integer within realistic bounds.

#### 5. `app/api/games/submit/route.ts` (Modify)
*   **Type / Scope**: Next.js API Route Handler (Node.js runtime).
*   **Rationale**:
    1. Adjusts Zod `durationMs` schema to enforce strict physiological limits (`z.number().int().min(3000).max(600000)`), rejecting submissions faster than 3 seconds or slower than 10 minutes.
    2. Adds structured diagnostic server logging (`console.error("[SUBMIT_REJECTED]", ...)`) containing user ID, Zod error issues, and incoming payload properties whenever validation fails, while maintaining generic client-facing error text (`"Invalid game submission."`).

#### 6. `tests/games.test.ts` (Create)
*   **Type / Scope**: Unit Test Suite (Vitest).
*   **Rationale**: Verifies game submission schema validation, physiological duration limits (rejecting < 3,000ms, rejecting > 600,000ms), and question grading logic with synthetic answers.

### Verification Plan

*   **Compilation / Typecheck**: Run `npm run typecheck` to confirm zero TypeScript compilation errors with the new `auth.config.ts` and `middleware.ts`.
*   **Linter**: Run `npm run lint` to guarantee clean code style and Next.js rule compliance.
*   **Unit Tests**: Run `npm run test` to verify all Vitest tests pass.
*   **Build Verification**: Run `npm run build` to confirm the Next.js App Router and Edge Middleware bundle successfully.
*   **Manual End-to-End Verification**:
    1. Sign in to an account → Navigate to `/login` and `/register` → Confirm immediate redirect to `/dashboard`.
    2. Play Number Rush from start to finish → Submit 5 answers → Confirm successful score calculation, XP award, and streak increment without "Invalid game submission" errors.
